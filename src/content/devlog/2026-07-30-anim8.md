On Thursday, I sat down and researched other games in the same genre as mine. I wanted to know what worked for them and what didn't so that I could focus on implementing the things that will matter most to players. For creature collectors specifically, these things stood out: companionship, collection hunting, and build variety. Positive and negative reviews tend to circle these themes. 

I decided to take a look at two games in particular: **Monster Sanctuary** and **Siralim Ultimate**. These games are closest to what I want Script Kitties to be in terms of style and depth, so I knew they were the ones to dive deeper on. I found YouTubers that played these games and studied their reactions to see what they liked the most and what they found frustrating. I played the games as well to get the feel of the gameplay first-hand.

And the very first thing I noticed these games had which mine didn't was animations.

#### Challenges

Of all the systems I've implemented in game engines over the years, I've never done animations. Mostly, this was practical: animations are time-consuming to create and serve as visual flourishes, not typically core game mechanics, so focusing on them first didn't make sense. I still believe this is true, but I'm finding out that focusing on animations last makes even less sense if you want to sell a game.

I found it difficult to wrap my head around how animations would work at first. Fundamentally, animations are just values changing over time. If you want text that floats up on the screen, you adjust its position. Fade? Opacity. Sprites? Frame index. This part, I get. 

What I struggled with was sequencing animations and having the game wait on them to complete. In battle, for example, when a creature attacks, there may be a wind-up animation, followed by a leaping animation, then a landing animation. And the player shouldn't be able to initiate another attack during this time. 

#### The Loop

If you're not familiar with game engines, they boil down to a single while loop. You update the game state and then draw it on the screen. Each iteration of this loop is a frame, and for a game running at 60 FPS, this loop runs 60 times per second.
```cpp
while (true)
{
    Update();
    Render();
}
```

To maintain at least 60 FPS, each iteration of the while loop must take no longer than ~16ms. So how do you play an animation that lasts 250ms? This is pretty straightforward: keep track of how much time has passed between each `Update` and when 250ms has elapsed, the animation is over.

```cpp
Update(delta) {
    elapsed += delta
    if elapsed >= 250ms 
        destroy()
}
```

Okay, not too bad. But what about sequencing animations? Well, you could go the callback route:
```ts
StartAnimation("wind_up")
    .then(() => StartAnimation("leap")
        .then(() => StartAnimation("land")
            .then(() => StartAnimation("creature_hit"))
        )
    )
```

Which... sort of works until you need to wait on multiple animations to complete before playing another. And it's awful to read, which I know from experience. My first real job after college was at a startup building dynamic web apps using jQuery. This was before JavaScript added support for `async`/`await` so _everything_ was a callback. Kids these days have it easy.

#### Speaking of async...

In Lua, there's a special type called a _coroutine_. Coroutines are special because they can be suspended and resumed later. And what's even _more_ special is how they get suspended. A coroutine runs either until completion _or_ until a `yield`:
```lua
co = coroutine.create(function()
    print("1")
    coroutine.yield() -- suspends the function
    print("3")
end)

-- elsewhere
coroutine.resume(co)
print("2")
coroutine.resume(co)

-- prints: 1, 2, and 3 on new lines
```

Why is this useful? Well, `yield` accepts arguments which can be used to specify _wait conditions_, like "yield for 250ms" or, importantly for our use-case, "yield until this animation is done". What this means is that instead of the callback hell above, we get an easy-to-read, top-to-bottom sequence of events:
```lua
anim = StartAnimation("wind_up")
coroutine.yield(anim) -- wait until wind_up is complete
StartAnimation("leap")
...
```

The beauty is that this code reads like it's sequential but behind the scenes are a few lines of code figuring out whether a coroutine can be resumed or not:
```cpp
Update()
    for (Task : Tasks)
        if Task.WaitCondition.IsComplete()
            Task.Resume()
```

With that in place, I was able to create a simple animation that plays when using an item on a creature in combat:

```lua
Task.StartTask(function()
    local decal = Decal.new(...)

    coroutine.yield(Anim8.Scale(decal))
    coroutine.yield(Anim8.Motion(decal))
    coroutine.yield(Anim8.Fade(decal))
    decal:destroy()
end)
```

#### The Next Bits

It took about 4 days to implement the animation engine with coroutine support for scale, motion, and fade animations, but I also need sprite animations. I use **Aseprite** for all of my art and it has a really nice animation workflow as well. When you export an animation from Aseprite, you get a spritesheet, which is just a composite sprite containing all of your animation frames. 

![pl](/devlog/anim8/player.gif)
![spritesheet](/devlog/anim8/spritesheet.png)

But my game engine doesn't have support for spritesheets yet. During active development, I've found spritesheets to be very tedious to deal with without proper tooling, so each asset in my game is a separate file for now. This is the last major milestone before animations work in Script Kitties.
